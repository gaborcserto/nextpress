## NATIVE-01E · Account disclosure trial

The trial retained the existing Dropdown. The native prototype handled Escape and outside dismissal in Chromium and Firefox. ArrowDown left it closed and moving focus out by Tab left it open. WebKit skipped the profile link on Tab in the default test configuration. Matching the existing behavior and geometry would require custom logic. Safari/iOS and assistive technology parity remain unverified.

**Target:** [UserMenu](../apps/admin/src/ui/shell/UserMenu/UserMenu.tsx). It contains one profile destination and a sign-out command with error feedback, plus identity text. It is present in both shell layouts. The current [Dropdown](../apps/admin/src/ui/primitives/Dropdown/Dropdown.tsx) provides React open state, click/keyboard dismissal and menu-oriented behavior. Profile's size and behavior make it a representative trial. A future Dashboard Create disclosure can be reviewed separately.

**Proposed markup and behavior:** In supported browsers use a named button with declarative popover target and a stable React ID, controlling a non-modal auto popover. Render the profile item as a normal link and sign-out as a button with pending guard, persistent feedback on failure and existing routing on success. Use natural Tab and Shift+Tab and omit menu roles for this disclosure. Escape returns focus to the invoker. Outside click should allow the clicked destination to retain focus. Confirm closed content is outside the focus order and announcements convey expanded state in supported browser/AT pairs; derive explicit state from toggle events only if needed for parity. Route changes close the disclosure. No changes to authorization or sign-out semantics.

**Position and fallback:** Keep current desktop end alignment and near-full-width narrow layout. Use scoped CSS anchor positioning only where the actual positioning and overflow features are supported. Otherwise use tested viewport positioning with header offset or the current Dropdown if geometry cannot be maintained. Clamp size and positions to the visual viewport, safe areas and available block space. Feature-test Popover independently of CSS anchors. Keep existing Dropdown as the fallback for unsupported engines and behavior failures, including the earlier iOS partial-support range if needed. Render identical server and initial client markup; switch after capability detection without remounting a focused or open control. Verify that the direct Profile destination is usable if client enhancement fails. Keep existing native modal dialogs.

**Compatibility:** Baseline implementations include Chromium 114+, Firefox 125+ and Safari 17+, with earlier iOS 17–18.2 listed as partial. That coverage is a feasibility signal. The implementation gate is actual supported desktop and iOS browser/AT behavior, particularly light dismissal, menu announcement and focus restoration. [Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API), [compatibility table](https://caniuse.com/mdn-api_htmlelement_popover).

**Gate:** Exercise pointer, touch, keyboard open/close, Tab traversal, Escape from each action, outside focus, navigation, sign-out success/failure, simultaneous overlay, scroll, resize, 320px, 200% text, 400% zoom and no hydration warnings. Validate supported and unsupported branches, disabled-JS profile access, Chromium, Firefox, Safari and iOS, plus NVDA/VoiceOver. Compare against baseline Dropdown. Proceed if the browser owns dismissal and top-layer behavior with equal focus and mobile ergonomics and fewer custom listeners. Keep the current component if support or AT parity fails. Roll back by restoring the UserMenu Dropdown consumer and removing trial-only styling and branching. Record the decision before considering any other surface.
