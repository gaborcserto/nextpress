# ADR-004: Page paths and navigation menus

- Status: Accepted

Pages keep the existing self-reference and a nonnegative sibling order. The Admin hierarchy action serializes moves in PostgreSQL, checks the previous parent and order, checks the proposed ancestry and descendant depth, and saves the parent and order together. The maximum is eight Page levels. Administrators and editors can manage the hierarchy. Authors continue to use their existing content permissions. A Page with children must be cleared of those relationships before deletion. Home remains at the root.

Canonical paths use the published ancestry and current slugs. They use the existing language prefix, for example `/en/company/team`. The existing `/pages/:slug` route remains a compatibility URL and supplies canonical metadata. The chosen Home Page uses `/` within each locale. Reserved roots remain owned by the application. Legacy conflicting slugs have a canonical fallback under `/pages`. Global slug uniqueness is retained for compatibility with legacy slug lookups and existing content writers. Historical nested paths return 404 when they no longer identify current content. No redirect records are created. Menu references follow Page IDs and always use current canonical paths.

Menus, items, and location assignments have separate records. Menu items use stable IDs scoped to their menu. Managed destinations store a content or taxonomy ID. A public response omits a deleted or ineligible destination and its subtree. A Page and all its ancestors must be publicly eligible. Menu items also support explicit local paths, HTTP(S) destinations, and grouping labels. Limits are five levels and 200 items per menu. Admin-only snapshot writes validate the tree and apply a version check and a PostgreSQL lock. Each location has one assignment. Release an occupied location before assigning it to another menu. Significant changes are logged through the existing correlated audit logger.

The additive migration installs a default Header with Home and Posts and imports legacy Header and Footer placements in title and slug order, up to each menu's item limit. The initial menus contain production-safe links and existing content references. The old placement fields remain readable for compatibility. The public shell uses the managed menu projection. The public shell consumes label, destination, tab preference, and hierarchy position from the API. Classic and Modern share Header and Footer rendering with Minimal. Minimal also supports a Sidebar that occupies space only when it has visible items.

The shared shell serves Live Preview and Saved Preview using saved menus and published destinations. Preview content authorization and origin checks remain with the existing preview flow. Unsaved menu editing stays in Admin. Web uses request-scoped React memoization and no-store delivery. This trades an API read per render for consistent publication and menu updates without cross-application invalidation. PERF-01 can evaluate the cost of this policy.
