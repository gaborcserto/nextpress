# ADR-002: API-owned media storage and delivery

- Status: Accepted

Existing PNG keys and the local storage configuration remain valid. New objects use a generated UUID with the verified format's extension. Original filenames are display metadata. The server verifies the declared MIME type against the bytes and decoder output, even when the filename extension differs. The database stores the stable asset identity, display metadata, ownership, and content relationships. Admin and Web use HTTP URLs and media IDs. A replacement object-store implementation can adopt the existing storage operations once the deployment topology is known.

Writes use exclusive filenames. Failed writes remove partial files when possible. A failed metadata insert checks for a committed row before removing its file. An inconclusive check preserves the file for reconciliation. Deletion commits the metadata change before removing bytes. A failed or interrupted cleanup can leave private bytes behind, and storage and PostgreSQL have independent commit boundaries. Cleanup failures emit `media.cleanup_failed`. Preserve the database and media root together and reconcile suspected orphans offline.

Assigning legacy cover, gallery, and structured document references and deleting a media row share the revision advisory lock. Restrictive PostgreSQL relations also protect cover, gallery, retained editorial revisions, and private working snapshots. Legacy text references are checked conservatively. The resulting conflict never returns document titles, draft identities, or revision details.

Public Web delegates media eligibility to the API and serves eligible files with no-store caching. Unpublished-only uploads require a permitted Admin session. Live Preview requests only the media referenced by the snapshot received from the editor. Admin retrieves the bytes under the current session and returns them through the verified preview window, origin, and session channel. The preview draws them in its document without changing Web's image-source policy.

## Image processing and delivery

New uploads store one sanitized image. Sharp auto-orients still images and removes source metadata. PNG and WebP use lossless output, JPEG uses quality 90, and AVIF uses quality 75 with effort 2. JPEG and AVIF undergo one lossy encoding during upload. GIF is fully decoded for validation, and its original rendering blocks and standard looping extension are retained. Non-rendering GIF metadata is stripped, preserving frame composition, delays, transparency and disposal. The API rejects APNG, animated WebP and AVIF sequences. The decoding stage identifies GIF frame counts for validation. The database continues using its existing metadata and stores no frame counts.

Limits are 2 MiB uploaded, 8 MiB stored, 8,192 pixels on either axis, 16 million decoded pixels across all frames, and 100 GIF frames. The GIF cycle limit is 60 seconds with each delay counted as at least 100 ms for budgeting. Playback preserves the original delays and loop count, including infinite looping. Two processing slots per API process limit concurrent work. Sharp's ten-second processing timeout applies to the native pipeline. It is a cooperative limit and excludes queue time and metadata inspection. Processing uses in-memory buffers and creates no temporary upload files.

Next.js 16.4.6 can self-host responsive optimization and negotiate output formats, with WebP as the default and AVIF available as an explicit option. Its default loader does not forward source authentication headers. It also caches optimized bytes beyond the source check and offers no per-asset purge API. A previously published cover, block, or Gallery image must become unavailable after its last qualifying reference is withdrawn or deleted. Both apps therefore use unoptimized Next.js images and deny optimizer source paths. Intrinsic sizing and browser lazy or eager loading still apply. Protected previews use the existing session transfer and a revocable object URL for opt-in GIF playback. The preview route alone permits image blobs in its CSP. [Next.js Image component](https://nextjs.org/docs/app/api-reference/components/image) and [16.4.6 optimizer implementation](https://github.com/vercel/next.js/blob/v16.4.6/packages/next/src/server/image-optimizer.ts).

A future cache or CDN must preserve public eligibility after reference changes, avoid caching protected media, and vary negotiated variants by the appropriate request headers. PERF-01 owns delivery measurements, invalidation, cache lifecycle and any justified derivatives. The Document Library can reuse storage ownership, exclusive writes and scoped delivery with separate validation and response rules.
